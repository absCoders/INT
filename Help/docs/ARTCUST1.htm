Planning a Software Documentation Project

The hardest part of any project is getting started. A good best practice is to plan the structure of your software documentation project before you begin writing topics. You can always make adjustments as the project progresses, but having a plan will ensure that your topics can “stand alone” (make sense no matter how the user finds them), that your topics will work for context-sensitive help, and that no important information is missed.

There are five steps to structuring a software documentation project, but you don’t have to do them in order. In fact, you should do 1-4 concurrently. This method will work in Agile shops; you can drop your content into each iteration, and design the Table of Contents incrementally. The structure is suitable for manuals also ― so you won’t have any issues if you are single-sourcing. This method will also work as a guideline to evaluate an existing project.

  1. List functionality

  2. Review the User Interface

  3. Collect the “housekeeping” topics

  4. Determine reference resources

  5. Design the Table of Contents (the architecture)

When structuring a Help system remember:

  • Help is architected much like a website. (It has all the same basic pieces: a TOC, Navigation, Topics, Search, etc.)

  • Well structured Help projects include well structured topics. See Structuring Help Topics for more information and examples.
